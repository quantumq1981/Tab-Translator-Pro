# Production audit — Tab Translator Pro (2026-11-18)

Independent review of `main` at `1c84ce1`. Scope: the loader (`index.html`), the pure engine
(`engine.tsx`), the UI (`TabDecoderPro.tsx`), the model/worker glue (`*-model.js`, `*-worker.js`,
`*-model-core.js`, `note-model.js`, `tab-view.js`), the deploy/CI workflows and the test suite.
Out of scope: the sibling apps (Chord Sheet Maker / Pro), vendored third-party bundles beyond
their pins, and ML model accuracy.

## Verdict: **Critical risks present**

Two critical issues: a known High-severity PDF.js vulnerability reachable from Scan mode, and
session/library persistence that silently doesn't work on Safari/iOS 15.2–18.x. Neither is
caught by the test suite. The engine itself held up well under fuzzing (below).

## Critical

### C1 — PDF.js 3.11.174 with eval enabled: arbitrary script in the site's origin (CVE-2024-4367)

- **Where:** `TabDecoderPro.tsx:697-699` (loads `pdf.js 3.11.174` from cdnjs), `:353` and `:3829` (`getDocument({ data })` with default options), `:3835` (`page.render` of an untrusted PDF in Scan mode).
- **Evidence:** advisory GHSA-wgrm-67xf-hhpq (High): PDF.js < 4.2.67 with `isEvalSupported` at its default `true` runs attacker-controlled JavaScript from a crafted font when the PDF is opened. Scan mode renders untrusted pages to a canvas — the exposed path. Path A (`extractTokens`) only reads the text layer, so it's less exposed, but the same document load happens there.
- **Impact:** script running as `quantumq1981.github.io` can read and change every same-origin store: this app's sessions and library, and the localStorage/IndexedDB/OPFS of every other GitHub Pages app on that origin, including Chord Sheet Maker Pro. The trigger is "open a lead-sheet PDF from the internet", which is the feature's purpose.
- **Fix (today):** pass `isEvalSupported: false` to both `getDocument` calls. It costs nothing: eval only speeds up glyph-path drawing. **Then:** move to `pdfjs-dist` ≥ 4.2.67, using its **legacy** build (plain 4.x uses `Promise.withResolvers`, which needs Safari 17.4, and that would break the iPadOS 16.7 device), served from the same origin with a SHA-256 pin.
- **Verify:** a static test that every `getDocument(` call passes `isEvalSupported: false`. Then, in headless Chromium, the public PoC PDF should run its payload before the change and not after.

### C2 — Session restore and the project library are unreadable on Safari/iOS 15.2–18.x

- **Where:** `TabDecoderPro.tsx:408-409` (`getFileHandle(…, { create: true })` runs before the `createWritable` check, so a zero-length `session.bin` is created), `:415-421` (`_opfsRead` returns that empty file), `:441-445` (OPFS is read before the fallback), `:1812` / `:1816` (`projectFilePut`/`projectFileGet` have the same pattern for `projects/<id>.bin`), `:973-980` (`openProject` accepts an empty `Uint8Array`, which is truthy, and saves it as the session).
- **Evidence:** MDN and caniuse list `FileSystemFileHandle.createWritable` as Safari / iOS **26+**, while `getDirectory`/`getFileHandle` exist from 15.2. (The comment at `:403-404`, "Safari 16.4+", is wrong.) Running the app's own functions against that shape gives `save → "ls"` (fallback written) but `read → 0 bytes`.
- **Impact:** on every iPhone/iPad not on iOS 26, including the owner's first-generation iPad Pro (stuck on 16.7):
  - "Close the tab, your chart is back" never works.
  - Every library project, audio included, opens as an empty file.
  - Opening a project overwrites the last good localStorage session copy with `""`.
  - The IndexedDB copies are intact, so a fix recovers existing libraries.
- **Fix:**
  - Check `createWritable` **before** `getFileHandle(…, {create:true})`.
  - On read, treat a 0-byte OPFS file as absent and read the fallback.
  - In `openProject` and restore, reject `!bytes || !bytes.length`.
  - Delete stray empty `.bin` files once.
- **Verify:** move the session/library storage helpers into a small module with injected `storage`/`localStorage`/IndexedDB and unit-test them against three mocks: Safari 18 (no `createWritable`), Safari 26, and OPFS failing mid-session. The proof script used for this audit is that test in its simplest form.

## Major

### M1 — Saved metadata and saved file bytes can describe different files

- **Where:** `TabDecoderPro.tsx:431-438` (`saveSessionFile`): an OPFS failure falls back to localStorage but leaves the older OPFS file, which is read first. The `"none"` path (> 3 MB with no OPFS writer, or a quota error) leaves the previous bytes in place. `:718`, `:773` start the save without awaiting it while the effect at `:892-905` writes the metadata straight away. The metadata carries nothing tying it to the bytes.
- **Evidence:** the proof script shows both cases: OPFS works for file A and then fails for file B, giving A's bytes back; localStorage holds A and then B is over 3 MB, giving A's bytes back.
- **Impact:** a restore applies file B's chord overrides, note edits (`scoreEdit.target` matches because the name comes from the metadata), part index and string shifts to file A's music. It then saves that metadata again (`:958`) and files a library project named B that holds A's bytes (`:957`). The error spreads into exports and the Pro handoff without any warning. The same result follows if the tab dies between the metadata write and the OPFS write.
- **Fix:**
  - Save the bytes first, then write the metadata with `{ size, sha256 }` of the saved bytes, from the resolved save.
  - Whenever one store succeeds, remove the copy in the other store.
  - When every store fails, remove the stale bytes **and** the edits in the metadata.
  - On restore, check size and hash; if they don't match, open the file without edits and say so.
- **Verify:** the same mock-based tests as C2, plus a kill-between-writes case.

### M2 — A file that hangs or crashes the parser can freeze the app on every launch

- **Where:**
  - `engine.tsx:1676`: `_gpxReadFS` sets the outer `offset` to the last data sector. A backward sector pointer sends the scan back to the same file entry, so the loop never ends. This is a port of alphaTab's `GpxFileSystem`, which has the same flaw.
  - GPX is parsed on the main thread (`TabDecoderPro.tsx:519-530`).
  - The decode handoff saves the bytes **before** parsing them (`:819`, parse at `:833`).
  - The restore runs on every launch (`:908-960`) with no in-flight marker.
  - There is no React error boundary anywhere.
- **Evidence:** a hand-made 16 KB `.gpx` (BCFS, one file entry whose sector list ends on an earlier sector) runs past every timeout.
- **Impact:** if a sibling app hands over a bad GPX while an older session exists, the page freezes, a reload restores the same bytes, and it freezes again on every launch. The same holds for any input that runs a phone out of memory during parsing; iOS reloads the page, which restores the same file. Today the only recovery is clearing the site's data, which also deletes every other app's data on that origin. The 405-score render sweep found no throw today, so the missing error boundary is a latent part of the same failure mode.
- **Fix:**
  1. Bound `_gpxReadFS`: keep a set of visited entry offsets, or cap iterations at `data.length / SS`. This doesn't change any valid file.
  2. Save the decode handoff's bytes only after a successful parse.
  3. Add a `ttp:restore:inflight` marker, like the existing `ttp:stems:inflight` and `ttp:beat:inflight` markers. If it is still set at launch, show "Restore anyway / Start fresh" instead of restoring automatically.
  4. Add a top-level error boundary with a "Start fresh" button.
- **Verify:**
  - A regression test with the crafted GPX: it must stop with an error within 1 s, and the 5 corpus `.gpx` files must give byte-identical scores.
  - An e2e test: set the marker, reload, and assert that no automatic restore happens.

### M3 — Failed heavy jobs are re-run on the page's thread

- **Where:**
  - `guitar-model.js:41-42` retries on the main thread whenever the error matches `/worker|module|import/`. That includes its own `"guitar worker crashed"` message from `:38`. This breaks the rule documented in `drum-model.js:8-10` and `stem-model.js:118-120`: never retry minutes of WASM on the page.
  - Every `*OffThread` wrapper in `TabDecoderPro.tsx:525-645` (and `:2052`, `:2215`, `:2689`, `:5004`) falls back for **any** error, including engine exceptions and `RangeError` allocation failures.
  - One worker crash switches the engine worker off for the rest of the session (`:490`).
- **Impact:**
  - A worker-side out-of-memory error or crash becomes a frozen or killed page on phones, which is the failure this design exists to contain.
  - An engine error on bad input runs the computation twice, the second time blocking the page (analysing a 4-minute song took about 2 s on a desktop-class core).
- **Fix:**
  - Fall back only when no worker exists (`"no engine worker"` or a construction failure); report engine errors as they are.
  - Remove the guitar retry.
  - Let `_getEngineWorker` try again after a crash instead of latching `_engineWorkerDead`.
- **Verify:** a unit test that a wrapper given a fake RPC that rejects with an engine error does **not** call the main-thread function, and a static guard against a main-thread retry in `guitar-model.js`.

### M4 — Launch depends on four CDNs with no integrity pinning, and the source is transpiled in the browser on every launch

- **Where:** `index.html:27` (Babel from unpkg, no `integrity`), `:114-115`, `:154-158` (React from esm.sh, which builds bundles on its server), `TabDecoderPro.tsx:697-699` (PDF.js from cdnjs), `stem-model-core.js:49-55` (ONNX Runtime from jsDelivr), `note-model.js:36-37` (TF.js and basic-pitch from esm.sh).
- **Impact:**
  - A compromise of any one of these CDNs has the same reach as C1: the whole origin.
  - An outage at unpkg or esm.sh means the app cannot start.
  - Each launch downloads 3.2 MB of Babel and transpiles 1.4 MB of source: 1.5–2 s on a desktop-class core, several times that on older iPads (not measured on a device).
- **Fix:**
  - Transpile at deploy time in `pages.yml` (CI already installs `@babel/standalone`), keeping `index.html`'s in-browser path for development.
  - Serve React, React-DOM, PDF.js (≥ 4.2.67, legacy build) and ONNX Runtime 1.23.2 from the same origin, with SHA-256 pins checked in `npm test`, as is already done for alphaTab and svguitar.
  - Until then, add `integrity` to the static `<script>` tags.
- **Verify:** a Playwright launch with every third-party host blocked must start the app and load a model.

## Remaining risks and blind spots

- **Not checked on a device:** the CVE was not reproduced in this app (the rating rests on the advisory and the code path); the WebKit localStorage quota figures; Safari launch time.
- **Shared origin:** every app on `quantumq1981.github.io` can read and write each other's storage. The handoffs depend on this, so any XSS or CDN compromise in one sibling app reaches this one. It can't be fixed inside this repo without separate origins.
- **Limits of the testing:** the fuzzing was random mutation (600 cases) plus 13 hand-made cases, not coverage-guided. The 15k-line engine's numerical correctness relies on the existing suite and the sweeps above, not on line-by-line review. The vendored bundles (alphaTab, neural-separate, svguitar) were checked only against their pins.
- **GitHub Pages headers:** Pages can't send CSP, COOP or COEP headers. A `<meta>` CSP is possible but needs `blob:` script sources for the loader, and an allow-list of hosts doesn't stop a CDN compromise; SRI or same-origin copies do.
